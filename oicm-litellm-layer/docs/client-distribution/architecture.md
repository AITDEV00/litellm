# Architecture (v2 — gateway slice)

> Revision 2. The original design (separate artifact pod routed by nginx
> path) was rejected in review: it adds a second serving deployment and
> ingress complexity for no benefit, and it cuts the artifact surface off
> from the gateway's own state. The same-origin chain now lives **inside the
> running litellm gateway as an OICM vertical slice**, following the exact
> pattern the repo already uses for voice routes.

## Host model

```
                 litellm.ecouncil.ae:443
                          │
                   nginx ingress (unchanged)
                          │  /  ->  litellm-proxy:4000
                          │
                 litellm gateway pod (unchanged deployment + 1 volume)
                          │
        ┌─────────────────┼──────────────────────┐
        │                 │                      │
        ▼                 ▼                      ▼
   /v1/*, /ui       /install                /mirror/*
   (upstream,       (slice router:           (StaticFiles mount on
    unchanged)       generated script)        the artifact volume)
```

No ingress changes at all. The existing `Prefix /` rule already delivers
`/install` and `/mirror/*` to the gateway; the slice simply registers the
routes.

## Why in-app (the review decision)

- **Uniformity.** One deployment, one ingress rule, one thing to monitor. A
  second pod plus two new ingress paths is a whole component whose only job
  is `sendfile()`.
- **The gateway has memory; the artifact pod would not.** The slice runs
  inside the app, so `/install` is generated by code that can read
  `general_settings`, the prisma client (DB), and the request host — so the
  script it emits always carries the gateway's own canonical base URL
  without anyone hand-editing it. A future authenticated variant (see
  [security.md](security.md)) can take `Depends(user_api_key_auth)` and use
  the caller's key/team to personalize what it emits. None of that is
  possible from a separate static pod.
- **Upstream precedent makes it native, not a hack.** The app already serves
  the entire Admin UI via `app.mount("/ui", StaticFiles(...))` and mounts
  `/swagger` the same way; OICM already serves custom routes via a
  self-contained `APIRouter` slice (`litellm/proxy/voice_routes.py`) pinned
  by drop-detection tests. Serving install artifacts is the same two
  mechanisms, one more time.

## The slice

Location and shape, following the voice-route pattern exactly:

```
litellm/proxy/client_distribution/
├── __init__.py          ← re-exports router
└── routes.py            ← the slice: APIRouter + /install handler
```

- `routes.py` builds a standalone `APIRouter` (tags: `["client-distribution"]`)
  and lazily imports `proxy_server` module globals inside handlers where
  needed — the same circular-import avoidance documented at the top of
  `voice_routes.py`.
- Wiring is one line in `proxy_server.py` next to the existing voice-route
  mount: `app.include_router(client_distribution.router)`, plus one
  `app.mount("/mirror", StaticFiles(directory=...))` next to the existing
  `/ui` mount.
- **Drop-detection tests** pin both wirings in
  `tests/test_litellm/proxy/test_oicm_drop_detection.py`
  (`test_client_distribution_router_mounted`,
  `test_client_distribution_static_mount_present`), so an upstream merge that
  clobbers the two lines fails a test, not production. This is the established
  merge-safety mechanism for every OICM slice.

### What the slice serves

| Route | Mechanism | Content |
|-------|-----------|---------|
| `GET /install` | router handler | POSIX bootstrap script, **generated at request time** (see below) |
| `GET /install.ps1` | router handler | Windows variant (deferred, same generator) |
| `GET /mirror/*` | `StaticFiles` mount on the artifact volume | uv tarballs/zips + `.sha256`, wheelhouse, Python builds, `manifest.json` |

### Why `/install` is generated, not a static file

This is where being in-app pays for itself. The handler reads the gateway's
own notion of its public URL (an env/config value, e.g. `LITELLM_PUBLIC_BASE_URL`,
with the request host as fallback) and the currently adopted CLI version
(`manifest.json` on the volume; a DB-backed source is a possible later step),
then emits the bootstrap script with those values baked in. Consequences:

- The script never contains a stale or hand-edited gateway URL.
- Version adoption (manifest swap on the volume) changes what every new
  `/install` fetch emits, with zero script redeploy.
- The template lives in the slice, versioned with the code, testable
  (unit test: render with a known manifest + base URL, assert the three
  origin overrides appear — a drop-detection-style behavioral test).

The template body itself is unchanged from
[installer-script.md](installer-script.md): a fork of upstream's
`scripts/install-cli.sh` with the three origin modifications. What changes in
v2 is only *who serves it and where its placeholders get filled*.

## The full first-run flow (client-visible, unchanged from v1)

```
curl -fsSL https://litellm.ecouncil.ae/install | sh
        │
        ▼
  [install script]                    (runs on the dev machine)
        │  uname -s, uname -m, libc detect
        │  GET /mirror/manifest.json
        ▼
  install/upgrade uv  ──── GET /mirror/uv/<pinned>/uv-<target>.tar.gz
        ▼
  uv tool install 'litellm[cli]'
        │   --no-index --find-links https://.../mirror/pypi
        │   UV_PYTHON_INSTALL_MIRROR = https://.../mirror/python
        ▼
  lite -> ~/.local/bin/lite
        ▼
  lite config set base_url https://litellm.ecouncil.ae
        │   (may already be baked by the script; harmless if repeated)
        ▼
  lite login  ->  lite configure / claude / codex / opencode / pi
        │   each fetches GET /v1/models with the user's key
        ▼
  done
```

Per-key personalization remains client-side (the stock CLI's
`agent_model_sync_env` behavior); the served script stays generic. The
slice's ability to authenticate `/install` is a *future* option, not the v1
behavior — the bootstrap paradox (key needed to fetch the installer) is
solved by leaving the artifact routes public and doing personalization after
the CLI exists.

## Sizing and isolation inside the gateway

- Static file serving through `StaticFiles` is the exact mechanism upstream
  already uses to serve the multi-MB Admin UI bundle; the artifact set (a few
  GB on disk, see [mirror-content.md](mirror-content.md)) adds no
  per-worker memory beyond the mount.
- The volume is mounted **read-only** into the gateway pod (the pod never
  writes; the sync job does), matching the existing `hooks` and `assets`
  readOnly volume pattern in the deployment.
- Artifact traffic and `/v1` traffic share the pod, so a pathological
  download storm competes with API traffic. Mitigations if it ever matters:
  nginx `limit_req` on `/mirror` paths (one annotation on the existing
  ingress, no new component) — noted, not built.
- Multi-replica caveat: today the gateway is a single pod; if it ever scales
  out, the artifact volume needs `ReadWriteMany` (Longhorn RWX) or the
  artifacts bake into the image instead. Tracked in
  [open-questions.md](open-questions.md).

## What stays untouched upstream

- `litellm[cli]` package: byte-identical PyPI wheels (mirrored).
- `uv`: byte-identical pinned release artifacts (mirrored), installed by
  upstream's own installer logic.
- The proxy's config, auth, model list, routing: unchanged apart from the
  two wiring lines the drop tests pin.
