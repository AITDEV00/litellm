## Findings

### R1 (HIGH): the actual uploaded installer contains unfilled placeholders and cannot run

`mcp-source-link/install.sh` has literal placeholders. Its own comment says the release
publisher substitutes them. `scripts/publish-source-agent-release.sh` base64-encodes the
file verbatim, without substitution or validation. A real publication therefore serves:
`base="__BASE__"` and `ExecStart=__STATE__/source-link connector`, with unresolved version
and checksum too.

`tests/unit/proxy/client_distribution/test_source_agent_distribution.py::_installer` performs
the replacement only in the fixture, independently of the real publisher. That makes the
suite pass while removing precisely the production defect.

Required fix: follow the existing `/install` distribution decision recorded at
`../docs/client-distribution/source-agent-releases.md`. Upload a RustFS-resident
`templates/source-agent-install.sh.tmpl` via admin-authenticated raw artifact PUT through
the gateway. `/install/source-agent` must select the active version from its validated
source-agent manifest and safely render the template's base URL/version/hash. Do not
leave publish-time shell interpolation as unimplemented. Test the exact artifact uploaded
by the real operator command, download it through the gateway, and execute on a clean HOME
This is required for B2 and B6; no third distribution protocol is wanted

### R2 (HIGH): no-gateway-environment path after successful CLI setup

The installer now runs `init`, then writes a unit with only
`ExecStart=.../source-link connector`. It no longer points `connector.env` at the gateway URL
or supplies any alternative URL configuration. Yet `runConnector` rejects the request before
even reading the identity unless `MCP_SOURCE_LINK_PUBLIC_URL` is set, and `connector.Run`
again requires that env or fails. `setup` writes `gateway_url` only to bootstrap JSON and
writes `user.key` plus `identity.json`; those stored values are never used to derive normal
runtime gateway configuration.

A fully successful interactive bootstrap therefore leaves an installed service that cannot
start. On a source host without the manual legacy env file, the user must still configure the
service by hand.

Required fix: have startup resolve the persisted gateway URL in a single well-defined config
precedence, matching the identity's previously bootstrapped gateway. Environment overrides
must stay intentional. The generated unit must not depend on an uncommented path an
ordinary user was never taught to finish. Cover noninteractive enabled/restarted services,
not only the direct Go setup helper.

### R3 (HIGH): a fresh unauthenticated user cannot reach `/sso/cli/password`

The route has no public-route exemption, so normal deployments require an auth key before
entering the new function. A newly provisioned user who has no key yet is exactly the user
this endpoint is meant to bootstrap.

Required fix: deliberately allow only the narrow password-login path through the auth
boundary, without making worker/enrollment routes public. Do not open a generic wildcard
for other SSO calls. Add a real gateway route test with no Authorization header, normal
enabled-auth and correct password-verification/identity behavior. Include administrator
rejection and rate limiting.

### R4 (HIGH): every ordinary connector password login creates two durable keys

`authenticate_user` is the UI sign-in helper, not password verification alone. For an
ordinary user it internally calls `generate_key_helper_fn` with no explicit expiry and the
password-session metadata but no restricted allowed routes. Then the new endpoint calls it
again and creates a separately scoped, durable connector key. The admin rejection happens only
after `authenticate_user` has already persisted an admin UI virtual key, so the 403 does not
undo that already-issued UI credential.

This weakens the precise user-scope/least-duration contract and makes duplicate durable
keys on every retry or reconfiguration. Despite the admin-choice message promising no long-
lived admin credential, a prior admin UI virtual key has already been created by that point.

Required fix: split verification from UI key/session issuance and reuse the verification
component here; issue only the intended ordinary, minimally scoped, owner user key after all
authorization checks. Consider existing scoped-key lookup/reuse during safe retry. Do not
preserve or mint a dashboard/session token as part of connector login. Test actual created
rows/keys and metadata, including admin deny and retry, not only that a returned key parses.

### R5 (HIGH): repeated source enrollment can re-pend approved content and promote it

`store.enroll` updates an existing source's catalog fingerprint/target and resets its
connectivity status to pending *before* registration conflict is resolved. If an admin later
approves, a same-owner reconnect/payload re-run with altered source catalog is caught as
pending-resumable: previous catalog/target/evidence never reaches pending_source_resume.
The new artifact is already served under the same stable artifact URL registered with the MCP
row. Once the worker reattaches, its matching new fingerprint promotes source connectivity.

Pending-source approval filtering protects gateway dispatch until approval, but the source
artifact itself is mutable while still listed in that initially approved row. No new explicit
review necessarily gates the changed catalog after it rolls again. This is exactly the
pre-existing hazard the work order said did not disappear merely because resume was added.

Required fix: immutable content digest/identity comparison before any reused source state or
spec artifact is accepted. Pending resume must verify that the requested content and target
are exactly the existing enrollment's. Any content change needs a deliberate re-review path
or alternate source/version identity, not an existing-approved replacement. Test approved
then altered re-enroll byte-for-byte, including connectivity/artifact and approval effects.
R5 testing cannot treat a generic successful pending resume as repaired without this equality.

### R6 (MEDIUM-HIGH): `resume_peer` is not bounded to a proven lost bootstrap response

Every owner-authorized retry of an active label/target now returns the same live HMAC at the
stored generation. Requested dataset/proof-key mismatches are not checked. The same
credentials can be re-derived by an owner replay at indefinite later time, including when
already-redelivered elsewhere. No server acknowledgement exists, so it cannot distinguish
first-use loss from later requests. This is deterministic, not a new HMAC rotation, but it
changes the intended delivery contract and hides catalog/trust drift.

What is good: it does avoid a new arbitrary generation and does refuse draining/revoked and
changed target. Keep that.

Required fix: compare the full peer fingerprint (label,target,dataset,proof-key) when
retrieving. Reconcile and preserve registration metadata. Choose an explicit supported
reissue/revocation model for all active future retrieval and document whether credential
exportability under same user ownership is an accepted product decision, not claim it as
only recovery. Test an issued/redeemed acknowledgement if that is the chosen policy,
or explicitly test accepted repeated reissue of identical immutable registration inputs.
Do not invent fake client attestation.
An owner curl request is not proof it is the connector executable.

### R7 (MEDIUM-HIGH): initialization has no retry/backoff or resilient installed-resume loop

Previous `connector.LoadIdentity` retry behavior is gone. `setup.Initialize`/`Register` now
run exactly one HTTP operation cycle and return. A temporary 401,429, gateway-offline or
response-loss error returns directly out of `runInit`; the installer exits before enabling
the service. Meanwhile `runInit` refuses noninteractive operation completely, and an
unconfigured installed unit cannot perform stored-input resume on its own.

This contradicts the docs claiming 401/429 is retried and shows a missing operational
recovery requirement even though the retry label classification is correct. No retry helper
is invoked. Making correct 409 classification terminal does not implement transient retry.

Required fix: restore a bounded backoff at the orchestration layer with a fatal-action-needed
route for known auth/revoke conflicts. Allow rerun from valid stored state without replacing
the identity or credentials, and do not require new credentials each retry. Proper terminal
failure must leave a clear actionable error for the user. Reconcile after worker response
loss and corruptly/unavailable disk, not just an HTTP 503 test fixture.

### R8 (MEDIUM-HIGH): revocation replacement not implemented as an operator workflow

The change leaves B3 as "defined, terminal by design": administrators use a fresh label in
another manual worker POST. Existing valid identity is returned unchanged by `Initialize`,
there is no supported reset/replacement CLI workflow, and the privileged lifecycle/revoker
call path unchanged. Terminal classification of old identity is not on connector restart;
the tunnel keeps retrying drifted/admission errors generically.

No complete administration runbook is documented or exercised either. Connector users cannot
recover by themselves: valid old identity is reused by `Initialize`, and replacement requires
manual/admin REST calls and local file changes which are not present in the product workflow.

Required: finish the supported fresh-label/admin replacement path or an explicit confirmed
local reinitialization path. Preserve revocation's fencing and administrative governance.
Test the actual revoke -> new identity -> live connector sequence. A new connector run must
not treat invalid terminal admission as just another general connection retry.

### R9 (MEDIUM): no first-class authenticated dev path for external users

There remain separate transport/API paths:

- Dev gateway is reachable only via host-side port-forward REST (HTTP).
- Connector insists a URL be https on login/bootstrap and again at tunnel startup.
- Tunnel uses the public host which directs gRPC to the dev broker, while ordinary
  `/mcp-sources` and the installer default to prod on that host.

Pure local unit tests cannot demonstrate that an external newly installed connector does
REST enrollment without sending the public REST to prod. The new work puts B4 in
"not a blocker" by naming a local port-forward without defining how the newly shipped
https-only product can actually use that forward for external users and its own separate
tunnel URL. It is not acceptable to claim that the forward alone meets the user's binary
input contract.

Required: either a suitably authenticated isolated HTTPS endpoint fronting dev REST+tunnel,
or intentionally distinct persisted/accepted endpoints and CA/trust for each. Use generated
TLS or documented internal TLS in actual connector probing. Do not weaken HTTPS checks
globally nor put dev new endpoints through prod. Show a complete real request from a source
machine with no cluster or pepper, admin approves, real MCP read eventually succeeds.

### R10 (MEDIUM): B6's safety conditions are not met

Besides R1, actual upload still isn't live-verified and no atomic/conditional active-pointer
exchange protects concurrent publishers. Immutable existing-version behavior protects only
when the existing binary already exists. Missing script means the active installation returns
409 for an already active version. Pointer activation has no digest validation of its own
and does not produce rollback tool support. Release payload maximum still counts base64 body
rather than actual binary only.

Use the **existing generic artifact upload through the gateway**, with the operator holding
per-environment Proxy Admin auth; nobody needs raw RustFS credentials. It sends raw bytes
(`PUT /install/admin/v1/artifact/{path}`) into RustFS. Follow
`../docs/client-distribution/source-agent-releases.md`: templates/source-agent-install.sh.tmpl
and source-agent/<version> chosen by validated active release metadata. Extend its immutable-
version validation and atomic handoff where needed. Do **not** call for a new third credential
path nor point direct S3/mc clients at the cluster store, which would bypass auth/manifest
consistency. There are pre-existing docs-vs-code gaps in its default upsert/ETag concurrency
claims, noted below and in the new distribution doc. The new slice must implement the promised
behavior, not assume text makes it exist

Required: validate full separate source-agent manifest, immutable asset tuples,
sequential publication/conditional pointer and rollback. Keep client/sidecar compatibility
metadata and include installer presence. Prove a real dev download while gateway bytes/pod
stay unchanged. Also correct no public-readiness `UP` legacy docs which claim CAS/If-Match and
manifest digest checks when current generic code does not implement them

### R11 (LOW): the initializer behavior and runtime inputs are not fully tested

There are no main.go tests which exercise installed service CLI no-identity/noTTY, or actual
terminal drive of init, argument handling, or service startup after valid identity. The
terminal password Secret helper trims both ends instead of preserving the supplied password.
Broad rescue in `Initialize` falls back to fresh prompts for
corrupt/bootstrap permission errors instead of requiring explicit remedy and can silently
reset the user's intended source changes. CA selection by environment is not used by either
real auth or bootstrap client despite TLS config support elsewhere. URL checker allows
unintended hostless/userinfo/path/query forms without robust normalization. Validate the
actual OpenAPI document before login since a free JSON file can fail only after key issuance,
and avoid logging spec contents arbitrarily.

### What is improved and should remain

- One binary now has `init`, with x/term password input rather than environment CLI secrets.
- Helper-based direct HTTPS auth, read-spec-from-file, owner-only atomic file writes, per-
  source deterministic worker labels, and better worker-response validation exist.
- Correct refusal of malformed identity source/target/nonhex credential before persistence.
- Real RemoteStore resume retains same row/id/generation and refuses revoked rentals.
- Gateway registration honors ordinary ownership, not body ownership; first-class control
  routes are not opened.
- Go formatting/race/compat gates keep the new code executable without regressing tunnel
  transport. Existing tunnel fencing is preserved independent of new auth behavior.
