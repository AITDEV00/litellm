    Dev source broker¶

    This dev slice exposes one approved OpenAPI service on a source host through the existing MCP gateway. The source host makes an outbound TLS WebSocket to the broker relay. LiteLLM authenticates and authorizes the normal MCP tool request before the private broker dispatches it to a healthy member

    The dev overlay is deploy/overlays/dev/mcp-source-broker. It creates one auxiliary Pod with broker and relay containers. The gateway contains no relay and starts no connector. Production is not enabled by this slice

    Reverse-h2 transport (second data plane)¶

    The same Go worker binary now carries a reverse-h2 transport alongside the WebSocket remotedialer, selected by MCP_SOURCE_LINK_TRANSPORT=reverse-h2 (default remains remotedialer). The connector dials one outbound TLS HTTP/2 session to the public gateway and keeps it alive; every forwarded request is an HTTP/2 stream on that session, so a held request costs stream state on the channel instead of a origin TCP socket per request. The protocol is a dispatch long-poll: the connector registers (POST /mcp-source-link-reverse), holds (POST /mcp-source-link-hold, the stream that carries liveness and generation fencing), polls for work (POST /mcp-source-link-dispatch, the relay answers one pending poll per forwarded request), and posts each origin response back (POST /mcp-source-link-respond). All four routes ride the reverse listener on port 8093 and are published through the same public host with the nginx GRPC backend protocol, which proxies cleartext HTTP/2 to the sidecar so stream multiplexing survives the ingress hop. Per-worker enrollment, catalog-fingerprint gating, generation fencing, revocation, and header stripping are identical across both transports; the dispatch queue is bounded and slow connectors shed to HTTP 503 rather than buffering unboundedly

    Live reverse-h2 verification (2026-11-16)¶

    The reverse data plane was verified end to end on the dev cluster with a scratch origin fixture on the source host (fresh Ed25519 proof key, port 18084) and two enrolled workers (reverse-h2, reverse-h2-b) for source f804e8c9-a9c7-5824-a90a-837262788be8. All of the following were observed live, each through the public ingress https://litellm.ecouncil.ae/mcp-remotedialer-* (nginx to h2c grpc_pass to sidecar 8093):

    • Registration and liveness: the connector registered, held its session, and the probe loop admitted it with catalog_fingerprint equal to the enrollment's expected fingerprint; the broker's peers view showed the worker healthy
    • Auth gating: no-credential and wrong-credential calls to all four reverse routes returned 401, through the ingress and directly on 8093 (curl --http2-prior-knowledge, since the listener is h2c-only and correctly gives HTTP/1.1 an empty reply)
    • Data plane: GET /sources/{id}/source.json and POST /sources/{id}/echo.json?channel=... through the private dispatch port returned origin data with credentials_seen=false and cookies_seen=false
    • Concurrency: 8 parallel reads through one reverse session all returned 200 in under 0.62s wall
    • Fencing and lifecycle: revoke locked the connector out immediately (re-register 401, dispatch 503 with Retry-After: 1); drain stopped dispatch; recover minted a new generation and the connector rejoined with a freshly derived generation-matching credential; duplicate registration for a worker with a live session was rejected with 401 while the original session kept serving
    • User path: a virtual key scoped to the source's mcp_access_groups called read_source and echo_source through POST /mcp-rest/tools/call on the dev gateway and received origin data (isError: false), exercising gateway auth, MCP tool dispatch, the data-plane pool URL, the reverse long-poll, and the origin round trip

    Two latent defects surfaced and were fixed during the live run. The worker-enrollment INSERT bound its expires_at parameter without a ::timestamptz cast, so Prisma sent text and PostgreSQL rejected the insert (the enrollment route 500ed); both worker and enrollment inserts now cast explicitly. A pre-existing source row also carried the retired chisel value in remote_transport, which selection() correctly rejected; re-pointing the source with PUT /mcp-source-link-sources/{id}/selection {"transport":"remotedialer"} refreshed both the stored transport and the registered pool URL to the data-plane Service port

    A follow-up review pass tightened the reverse-h2 protocol itself. A forwarded request now carries a 90-second response deadline, so a lost respond can no longer leave the caller hanging until the session dies. Oversize dispatch payloads fail fast with 502 instead of being silently truncated, and origin bodies are capped at 760 KiB so the base64-inflated respond envelope always fits the 1 MiB wire limit; before that cap, a just-under-1-MiB echo wedged the connector dispatcher permanently because the relay refused the oversized respond without draining it (the handler now drains rejected uploads). Framing headers (Content-Length, Transfer-Encoding, hop-by-hop fields) are stripped from relayed responses so truncated bodies can never corrupt response framing, and the connector treats a non-204 respond as a lost session. All of this was re-verified live after redeployment: 8/8 concurrent reads in 0.5s, POST with credentials_seen=false cookies_seen=false, 401 auth negatives, near-limit and over-limit echoes failing fast (502 in under 1s) with the connector surviving and the session still serving, revoke lockout, and the gateway MCP user path (read_source, echo_source) returning origin data through a scoped virtual key

    Enrollment¶

    A proxy administrator posts a SourceCreate to POST /mcp-sources:

    {
  "owner": "source-owner",
  "alias": "private-openapi",
  "key": "admin-generated-at-least-16-chars",
  "expires_at": "2027-01-01T00:00:00Z",
  "target": {"host": "127.0.0.1", "port": 18080},
  "spec": "{\"openapi\":\"3.1.0\",\"paths\":{\"/source.json\":{\"get\":{}}}}"
}

    The source target allows loopback only and requires an explicit local service. An ordinary source membership stays in the authenticated relay authfile even when unhealthy; quarantine prevents tool dispatch, not subsequent recovery. Administrators can retrieve the existing connector installer whenever the source has been catalog-quarantined

    The source target is only a loopback host and port. Source identity is derived from owner and alias. The gateway saves the catalog object in the gateway-accessible artifact mirror, registers a stable private pool URL with LiteLLM, and grants that source its own MCP access group. Re-enrollment keeps its source, enrollment, connector lease, and relay credentials; it updates the target and expected canonical catalog fingerprint. It does not return another one-time token

    The connector transport is the hand-rolled reverse-h2 path in mcp-source-link/: the connector on the source host dials in (the gateway cannot make outbound connections, so the agent-initiated session is the only transport), the sidecar accepts it, and dispatch rides back over that session with a 64 in-flight cap and 8 concurrent origin round trips per connector. This path is fully verified live (steps 2, 3, 4, 7 below) but its wire contract is implicit Go structs on both ends, which is why step 9 spikes jhump/grpctunnel: any version of either side must keep connecting, degrading to less functionality rather than breaking, and that contract must be enforced by a versioned proto, not implied by struct layout

    Connector installation no longer has a per-source token installer; the Chisel relay text below is retained only as the 2026-11-13 historical record. The current contract is the client-distribution slice litellm/proxy/client_distribution/source_agent_distribution.py: an admin publishes a release pair (binary, release.json) through PUT /install/admin/v1/source-agent/release, and any source host runs the fixed script from GET /install/source-agent, which downloads the versioned pair, verifies the binary against the SHA-256 checksum embedded in the script, writes source-link mode 500, and renders a user systemd unit source-agent.service running source-link connector with environment from ~/.config/source-agent/connector.env (MCP_SOURCE_LINK_PUBLIC_URL, MCP_SOURCE_LINK_CONNECTOR_CONFIG). The unit only starts once the config exists; without it the installer leaves the binary installed and prints the gating message. There is no release signature and no signing key: releases were briefly signed with an Ed25519 key and the installer briefly verified that signature on 2026-11-17, and both were removed the same day as over-engineering. The publish route is admin-only and the checksum the installer enforces is derived from what the gateway itself published, so the signature protected nothing the admin gate and checksum do not already cover. A substituted binary that cannot speak reverse-h2 or present a valid enrollment credential fails at the broker regardless. The old release.sig.b64 objects from the signed era remain in the bucket as inert legacy bytes; the asset route no longer serves them

    Release 0.2.0 (2026-11-17) is the first reverse-h2 release and stays in the bucket as immutable history (SHA-256 03c607b6...702d00c). Its assets include a release.sig.b64 from the signed era that nothing reads any more. The pre-rename 0.1.0 release (retired WSS-era source-agent) also stays in the bucket as harmless legacy

    A release version is immutable once published: re-publishing a version that already has a source-link object returns 409, so a version number always names the same bytes

    Release 0.3.0 (2026-11-17) is the current release: the reverse-h2 source-link built by make mcp-sidecar-build (SHA-256 1242a6e1...b5269), with release.json pinning sidecar image manifest sha256:3ad55297...a3b7a4. It carries the round-trip caller-cancellation and shutdown-deadlock fixes, so connector hosts get a behaviour change beyond the installer script, not just a new checksum. The published 0.3.0 binary and manifest are unchanged by the installer-contract revert; only the served script changed. A republish of 0.3.0 returns 409 release version is already published and immutable with the stored bytes unchanged, and both 0.1.0 and 0.2.0 still serve their original bytes

    Calls¶

    Use an ordinary virtual key authorized for the source-specific MCP access group. No Chisel installation is needed on the caller's machine. The gateway creates OpenAPI tools from the saved spec and dispatches them to the pool URL without a trailing slash

    A healthy connector has a recent successful catalog probe and actual catalog fingerprint equal to the enrollment's expected fingerprint. Startup clears health timestamps. Different catalogs are quarantined rather than merged. The pool strips gateway authorization, cookies, and transport headers before forwarding. Retries are restricted to errors where the upstream connection was not established

    The fixture proof can use this request with READ_KEY:

    curl -fsS http://127.0.0.1:14003/mcp-rest/tools/call \
  -H "Authorization: Bearer $READ_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"server_id":"f804e8c9-a9c7-5824-a90a-837262788be8","name":"read_source","arguments":{}}'

    The returned CallToolResult.content[0].text contains JSON from the source's /source.json endpoint. For an echo tool, use {"channel":"dev-tool","body":{"text":"round-trip-through-chisel"}} as arguments. Validate the actual source marker and that its credentials_seen and cookies_seen booleans are false

    Port map (canonical)¶

    The broker Service litellm-mcp-broker-dev is the only gateway-facing address. Its named ports and the container listeners behind them:

    Service port Service name Container port Listener Who calls it
    8888 data 9092 (link-data) Go sidecar private dispatch: /sources/{id}/{path}, /v1/source-link/revoke The gateway's MCP pool URL, MCP_SOURCE_BROKER_DATA_PLANE_URL
    8093 link-reverse 8093 Go sidecar reverse-h2 ingress /mcp-source-link-{reverse,hold,dispatch,respond} and /grpctunnel.v1.TunnelService/* Source connector, reverse-h2 transport (the only transport)
    9091 remote-control 9091 FastAPI broker process (remote control) Administrator via port-forward

    8888 is the standard gateway-facing data-plane port: the gateway's registered pool URL is always http://litellm-mcp-broker-dev.adeo-litellm.svc.cluster.local:8888/sources/{id}, from the MCP_SOURCE_BROKER_DATA_PLANE_URL env var. The connector routes ride the shared 443 ingress, unchanged. The NetworkPolicy matches pod ports after Service DNAT, so it keeps listing the container ports. The 8092 WSS listener and its rd-worker Service port and Ingress were removed on 2026-11-17; reverse-h2 is the only transport

    Next steps¶

    The reverse-h2 transport is verified on dev as a single-replica data plane. Work is ordered by risk, and each step should carry its own live verification the same way this slice did. Revised 2026-11-17 after the service-topology review, and after the reproducibility audit:

    1. Release signing (REMOVED, 2026-11-17, not parked). Releases were briefly Ed25519-signed at publish and the installer briefly verified the signature; both were removed the same day as over-engineering. The publish route is admin-only, the installer checksum is derived from what the gateway published, and a substituted binary fails at the broker without valid enrollment credentials, so signing protected nothing the existing gates do not. The signing key existed only in /tmp and was destroyed after the removal. Reopen only if a real distribution channel appears that the gateway does not control, for example the binary being mirrored outside RustFS or an air-gapped host receiving the release over untrusted media; the enforcement point belongs at that channel's boundary.     2. Reproducibility. Everything deployed must be spawnable again from the Makefile and the committed manifests, with no shadow patches. Status: DONE (2026-11-17). The audit compared every broker object (Deployment, Service, NetworkPolicy, Ingress) field-by-field against the live cluster: MATCH, no drift, no out-of-band patches; the broker Secret is deliberately untracked in git and the CNPG secret is operator-owned. Both image builds were previously Makefile-unrecorded (the sidecar had no Dockerfile at all, the auxiliary recipe lived only in this doc with its Dockerfile deleted at db12cdb7946), and the RustFS-stored install binary was the retired WSS-era source-agent. All three gaps are closed: mcp-sidecar-release and mcp-broker-release-dev build, push, and roll from the Makefile (proven live: the pods' imageIDs equal the pushed registry manifests sha256:47f3b330... and sha256:641e085a...), both Dockerfiles are committed, and release 0.2.0 publishes the current reverse-h2 source-link through the admin release route. The vestigial fingerprint and relay-host-key keys on the broker Secret remain noted but unread by anything

    3. Service and port standardization. Both broker Services keep named ports, but the public data-plane entry is renumbered to the standard 8888 on the Service (gateway-facing dispatch), so no code or registration carries a magic number anymore: the gateway's pool URL moves into an overlay env var, the owning doc gets one canonical port map, and the parallel source-agent research relay is decommissioned once the broker path is proven (it has zero gateway references and doubles the review surface). The connector routes stay on the shared 443 ingress, unchanged. Status: DONE. The 8888 Service port, the MCP_SOURCE_BROKER_DATA_PLANE_URL env var, and the canonical port map above landed and were re-verified live; the research relay's Deployment, Service, Ingress, NetworkPolicy, secret, and overlay directory were all deleted on 2026-11-17 after the 8888 round trip passed (the install mirror still serves the source-agent release script, which is client-distribution surface, not relay surface)

    4. Multi-host failover. Enroll a second source host with its own origin and proof key, run both connectors concurrently, and verify request distribution and failover when one host stops. The pool already prefers least-in-flight members, but no test has exercised two live reverse sessions from different hosts. Status: DONE (2026-11-17). Two workers (failover-host-a on origin port 18084, failover-host-b on 18085, each with its own Ed25519 proof key and dataset) held concurrent reverse sessions; 12 dispatch calls split exactly 6/6 across markers; killing host A's origin moved all 12 subsequent calls to host B with zero failures while A's connector kept its session (the origin refused, dispatch shed, no poisoning); after one probe cycle the broker marked A healthy_at=NULL and excluded it from dispatch (8/8 to B); restarting A's origin re-admitted it within one probe cycle and distribution rebalanced 5/5 over 10 calls
    5. Load profile. The Pass 3 feasibility control held 100k SSE streams on one h2c connection at 610 MiB with a raw prototype; the shipped long-poll design has not been loaded past tens of concurrent requests. Run the Pass 3 harness against the dev deployment and record streams, memory per connector, and p95 dispatch latency, so the architecture claim is measured on the real protocol. Status: DONE (2026-11-17). Measured on the dev deployment through Service port 8888 with one reverse-h2 connector (load-host, uvicorn origin fixture on the source host) and a driver inside the broker pod, 10s runs, GET /source.json: 50 RPS 500/500 p50 77 ms p95 269 ms; 100 RPS 1000/1000 p50 553 p95 849; 250 RPS 2500/2500 p50 563 p95 855; 500 RPS 5000/5000 p50 538 p95 798; 1000 RPS 9998/10000 (two 502 origin timeouts) p50 546 p95 802 p99 951. The Python-thread driver saturated at 2000 RPS offered, so the true per-connector ceiling above 1000/s is not established (same driver caveat as Pass 3). Held streams: 32 and 64 concurrent 3s-held calls all 200; 128 concurrency sheds exactly at the designed 64 in-flight cap (64 x 200 + 64 x 503 with Retry-After), and memory was flat across the sweep within sampling noise: connector RSS 19.0-19.2 MiB, sidecar RSS 8-13 MiB (metrics-server), sidecar CPU 70-73 milli-cores at 500 RPS. Sustained overload wedges the single-process origin fixture, not the data plane: dispatch sheds 503 with zero memory growth and no session loss, drain is bounded by the 8 concurrent origin round trips per connector, and full recovery was verified after rest (200 RPS 1600/1600). The architecture claim is measured on the shipped protocol: a held request costs pending-queue entry plus h2 stream state, not a socket or buffer growth. In passing, two connector processes sharing one config re-confirmed duplicate-session rejection: the winner serves, the loser gets 401 with capped backoff
    6. Session and connector ownership. The dispatch long-poll ties a session to one pod; a multi-replica broker needs pinned placement plus fan-out or a shared queue. The debate, positions, and resume conditions live in MULTI-REPLICA-DESIGN-DEBATE.md; do not redesign here, and decide only when a replica increase is actually demanded
    7. Recovery tooling. After revoke, a worker is terminal and a new label must be enrolled by hand. Decide whether an admin-facing replace flow should mint the next label and a fresh connector config in one step, or whether terminal revoke stays manual by design. Status: DECIDED (2026-11-17), terminal revoke stays manual by design. Rationale: revoke is an emergency action and coupling it to automated credential minting widens the security surface at exactly the wrong moment; enrolling a replacement is one existing admin call plus the documented credential derivation, so the manual path costs seconds; no incident or demand has shown it too slow; and a replace flow would prejudge the parked multi-replica ownership design. Revisit only when a real recovery exercise shows the manual path exceeding an operator's incident budget
    8. WSS transport deprecation. Flip the sidecar to reverse-h2 only, soak, then delete the remotedialer code path, the 8092 WSS listener, its ingress route, and the rancher dependency tree. The comparison between the transports is complete; keeping both is a live security surface and a confusing dual path. Status: DONE (2026-11-17). The full regression suite was rebuilt for the reverse path (transport_test.go: synthetic credential digests, three-peer read sharing with revoke, drain-excludes-dispatch, revoked/stale-generation reconnect rejection) and passes under go test -race (1.3s), gofmt/vet/tidy clean.     Rename to source-link (2026-11-17)¶

    The Go module directory is mcp-source-link, matching the source-link binary it builds and the release name the distribution slice publishes. It was named mcp-remotedialer from the rancher/remotedialer WSS transport that step 7 deleted, and the stale name misdescribed a module that now implements two data planes, reverse-h2 and tunnel

    The rename covers every published surface, not just the directory: the connector routes /mcp-source-link-{reverse,hold,dispatch,respond}, the gateway's /mcp-source-link-sources routes, the sidecar's control routes /v1/source-link/{peers,report,revoke}, the MCP_SOURCE_LINK_* environment variables an installed connector reads from connector.env, the MCP_SOURCE_LINK_ENABLED broker flag, the link-data and link-reverse Service port names, the sidecar container name, and the image repository mcp-source-link-worker. The reverse ingress also gains the /grpctunnel.v1.TunnelService/ prefix for the tunnel plane

    Three strings deliberately keep the old name because each is stored state, so renaming it would silently invalidate live records: the remotedialer-credential HMAC domain in keys.py (it derives every enrolled worker's stored credential digest), and the remote_transport column's legacy 'remotedialer' value, which selection() maps to reverse-h2 at read time rather than rewriting rows at boot. New rows default to reverse-h2. Because the installed connector's env vars moved, a connector upgraded to a build before this rename keeps working against the old route names only if its broker also predates the rename; the two must be rolled together, which is why release 0.4.0 ships both

    1. Transport standardization on jhump/grpctunnel (IN PROGRESS, started 2026-11-17). The broker-to-connector pair must keep working across independent upgrades of either side: any client version connects to any server version, degrades to less functionality rather than breaking. The current hand-rolled reverse-h2 framing makes that contract unenforceable, and the bugs fixed in the 2026-11-17 smell pass (round-trip ignoring caller cancellation, shutdown deadlock while holding the runtime mutex) are exactly the classes of defect the library handles natively. Evaluation of six candidates (scratch clones in evaluate-delete-later/, 2026-11-17): rancher/remotedialer is the closest API match but is WebSocket-based, offers the server a general net.Dial into the agent's namespace, has an open concurrency-issue PR, and this repo already ran it in the WSS era and paid to remove it (commit 34aee32e104 built on it; step 7 records the removal); apiserver-network-proxy says in its README it should not be imported as a library; frp is standalone binaries; openconfig/grpctunnel is TCP-proxy-focused and explicitly not an official Google product; yamux is only a multiplexer and we already multiplex via HTTP/2. jhump/grpctunnel is the fit: reverse tunnel is precisely agent-dials-home, the server pushes typed RPCs down the agent-initiated stream, windowed flow control, per-RPC cancellation native, tunnel revision negotiation built in; single-maintainer risk noted. Spike scope: a dispatch.proto defining the RPCs the broker pushes (admission/probe/dispatch with a capability set exchanged at registration so old binaries degrade to less functionality instead of breaking), generated stubs pinned in the repo, sidecar hosting the tunnel handler and the Python broker dialing into it, and a compatibility soak gate: every broker release runs against the previously published connector binary. Two binding rules for the dispatch proto, decided before the first .proto exists: additive-only evolution (never renumber, never repurpose, never remove), and breaking changes require a deliberate new connector release, never a silent one. Reconnection does not resurrect in-flight requests; retry safety remains application logic because only the broker knows which origin operations are idempotent. Ingress carries gRPC over the shared 443 route with the backend-protocol: GRPC annotation on the backend leg. Acceptance for the spike: tunnel regression suite passes under go test -race, head-to-head benchmark against reverse-h2 at the step-4 load profile (50-1000 RPS, held streams, failover), and both-direction compatibility demonstrated (old stubs against new broker and new stubs against old broker) before any decision to replace the reverse-h2 path

    Step 9 first live result (2026-11-17). The tunnel plane now connects and serves end to end. The connector's first bug was silent: runTunnelConnector built the dial address with string surgery, so the scheme survived into the target (https://litellm.ecouncil.ae:443) and gRPC could not parse it, which killed every attempt on the dial timeout without a single server-side log line. grpcDialTarget now parses the URL, joins host and port, and defaults to 443, with a regression test that fails on the old scheme-keeping form. Diagnosis took three separate traps worth recording: the sidecar is FROM scratch so kubectl exec has no shell, the ingress access log never shows /grpctunnel.v1.TunnelService/ traffic because gRPC streams log at completion, and grpctunnel's Serve returns started=true once the reverse stream opens, so a healthy tunnel is indistinguishable from a stuck one unless the broker-side healthy_at moves. Live proofs with transport tunnel: worker reaches phase active with healthy_at set and catalog_fingerprint equal to expected_catalog; data-plane GET /sources/{id}/source.json returns 200; the origin marker reports credentials_seen=false and cookies_seen=false; 8 parallel reads all 200; no token and bad token both 401; unknown source 503. The probe also needs the origin to sign nonce + "\n" + source_id + "\n" + dataset_id + "\n" + canonical_catalog with the Ed25519 key whose public half is the enrolled proof_key, so a fixture that serves the right bytes but no X-Source-Signature leaves healthy_at null forever; that is production behaviour, not a bug

    Load testing the same day exposed the plane's second defect, and the 2026-11-18 root cause is worth the archaeology. Under sustained dispatch churn the tunnel died with RST_STREAM INTERNAL_ERROR and in-flight requests failed as 502s; the failure never reproduced in-process because it was not ours or grpc-go's. nginx error log at the exact reset instants: client intended to send too large chunked body: 1048608 bytes while sending request to upstream. The reverse tunnel is ONE client-streaming POST whose body accumulates every pushed RPC request for the tunnel's whole lifetime, and nginx's default client_max_body_size 1m (rendered inside the grpc location) kills that stream the moment the cumulative bytes pass 1MB, which under load is 15 to 50 seconds. Fix: nginx.ingress.kubernetes.io/proxy-body-size: "0" on the reverse ingress (commit pinned by tests/deploy/test_source_link_ingress.py), then a second full reload's worth of load verified clean: 17,624 dispatches in 60s at 64 in-flight with zero failures and zero resets, where the pre-fix tunnel died roughly every megabyte. Max concurrency measured the same day: the 64 in-flight cap is per connector and fail-fast (immediate 503 no eligible connector), and adding a second connector doubles it to 128, so capacity scales with connector count rather than degrading

    1. Per-connector in-flight cap removed (2026-11-18, commit 0b1a7001a47). The literal 64 in pool.go is now dispatchInFlightCap = 0, and pick only checks inFlight when the cap is positive. The fix in step 9 removed the proxy-body-size cliff that used to masquerade as a per-connector ceiling; nothing structurally requires 64 anymore, since every dispatch multiplexes inside one HTTP/2 stream and a held request costs only a goroutine plus a 64KiB grpctunnel flow-control window per message. To measure the real ceiling the dev sidecar was raised from 1/256Mi to 1 CPU/512Mi requests + 8 CPU/16Gi limits, an uncapped mcp-source-link-worker:jya0-v1.108.5 image was built and pushed (config digest 4fe6d79b9fc7cd...), and a held-request ramp was run against the live ingress with ONE clean connector and a 2s-slow origin. Clean ladder against a freshly deduped connector: 512 in 5.60s (p50 3.30, p95 3.79, all 200), 1024 in 10.59s (p50 2.08, p95 2.20, all 200), 2048 in 5.55s (p50 2.68, p95 2.81, all 200), 4096 in 73.06s (p50 36.65, p95 69.62, all 200). Sidecar metrics at 4096: 8m CPU, 192Mi RAM. The 73s wall is NOT the transport: the Python thread-per-request loadgen pegged its own 8 CPU cores and grew its RAM from 146Mi to 326Mi doing TLS handshakes and GIL serialization, and the extra ~70s were client-side. To find a real transport ceiling the loadgen must move off Python (wrk, vegeta, or Go). At 4096 the sidecar itself uses well under one core and ~200 MiB, so neither in-tunnel streams nor the new resources are the wall. The 8192 row was cancelled deliberately: further rows would measure only more client CPU starvation. Three measurement hygiene rules were learned the hard way: (a) one worker identity must have exactly one live connector process, any duplicates masquerade as transport flakiness via 401 session jockeying; (b) the narrowest ramp rows must complete in seconds or the test setup itself is broken, so always launch with mode=async, per-row timeout, and an append-only log with START/END markers; (c) broker pod IP changes on every rollout, so the direct to-pod load path must re-read status.podIP rather than reusing the cached 10.42.6.6

    The Go-driver follow-up measured 65536 fully successful dispatches through the real tunnel in 15.151 seconds after fixing transient probe-health eviction. Before the fix one two-second probe timeout cleared the connector's catalog fingerprint and readiness, producing large immediate 503 and 502 bursts despite the connector remaining alive. Transient probe or health-report transport errors now retain the last admitted catalog for 30 seconds. A fingerprint mismatch, revocation, generation fence, or closed session still makes a member ineligible. Generation fencing also applies synchronously in worker selection before asynchronous reconciliation.

    The full race suite covers transient probe timeout retention, expiry after the grace period, mismatch quarantine, and immediate generation fencing. The successful 65536 run, its resource use, the uncapped active connector, and the test-only h2c frontend are recorded in the concurrency record. That report also records the 131072 offer as inconclusive because it lacked a final result.
