    LiteLLM v1.108.5 application-side MCP execution¶

    Engineering handoff · 11 November 2026
    Target BerriAI/litellm tag v1.108.5 · commit 2a61f2114d45016bae77930903e65172cd8e762c. LTS release · Pinned source

    Architecture · Repositories · Client setup · Gateway changes · Verification · Runnable fixtures

    Architecture decision¶

    LiteLLM owns the approved tool catalog and makes every authorization decision. The application’s internet-connected environment executes approved calls. Stock harnesses connect to an ordinary MCP server in that application environment.

    Mount /mcp in the existing application backend when possible. Where a backend cannot host it, run the same handlers as a sidecar or a local stdio process. A harness configures one standard MCP server entry. Its normal model connection can continue to use LiteLLM. For applications that already own their tool loop, the existing LiteLLM Chat Completions handoff is an optional entry point into the same authorization and execution flow. MCP tool protocol · MCP transports · LiteLLM MCP configuration

    The network assumption is an existing approved path from the application to LiteLLM and an on-prem model path for inference. The gateway has zero public egress. Provider endpoints and credentials live with the application. Central input guardrails run before any outbound search. The application can also send the actual search result back through approved ingress for central screening when that policy is required.

    Component Owns Connects to
    LiteLLM Gateway Canonical tool IDs, descriptions and schemas, caller grants, guardrails, model routing The existing on-prem inference path
    Application MCP server or owned tool loop Caller mapping, tool-to-provider bindings, provider credentials, execution, and result handling LiteLLM’s approved ingress and the application’s search backend
    Codex, Claude Code, DeepSeek Harness, or another MCP host Model/tool loop, tool discovery, invocation, and any host approval UI The application MCP endpoint and its configured model endpoint
    Search provider or existing search aggregator Search execution and provider results Reached from the application environment

    Standard harness request flow¶

    sequenceDiagram
    participant H as Harness
    participant A as Application MCP server
    participant G as LiteLLM
    participant S as Search backend
    H->>A: tools/list
    A->>G: Read filtered catalog
    G-->>A: Approved definitions
    A-->>H: MCP tool list
    H->>G: Inference with discovered tools
    G-->>H: Function call
    H->>A: tools/call
    A->>G: Authorize exact arguments
    alt Approved
        G-->>A: Decision and final arguments
        A->>S: Execute with application credentials
        S-->>A: Search result
        A-->>H: MCP tool result
        H->>G: Continue inference with result
    else Denied or unavailable
        G-->>A: Denial or policy failure
        A-->>H: Tool error
    end

    The model leg shows a harness configured to use LiteLLM for inference. A host may use a different model endpoint and still use the same MCP server. If result policy requires gateway inspection, the application adds that check before returning the tool result. A hosted harness must be able to reach the application MCP endpoint. localhost refers to the harness’s own network namespace. MCP tool protocol · Codex Cloud networking

    Why these boundaries¶

    Decision Rationale and tradeoff
    Expose MCP from the application environment Standard tools/list and tools/call are sufficient for existing hosts. Placing the MCP server beside the app puts execution on the network that has the provider credential and internet access. The app must reach both LiteLLM and its search backend.
    Publish schemas from the LiteLLM catalog Permissions and definitions come from one authority. Provider package updates cannot silently change what the harness sees. A new tool or a breaking schema change still needs a compatible application binding.
    Reuse LiteLLM admission and guardrails behind an internal authorization-only route Central policy sees the exact arguments before egress and can block or rewrite them. One extra gateway round trip per call buys current policy enforcement and keeps the existing policy implementation authoritative.
    Keep the public interface standard and the gateway patch opt-in Harnesses can switch transport or model independently. The small private contract is between two services you control. Existing gateway-executed MCP servers keep their existing path.
    Deploy the integration with the application Both the application’s existing HTTP deployment and a sidecar can use public dependencies. Harness onboarding is a URL or launch command. You own the two small handlers and the provider binding, with no separate private Python package to distribute.
    Keep output policy explicit A pre-call check protects the provider boundary. Screening a result before returning it protects the harness and its downstream consumers. Screening a later inference message protects only the model input through that route.

    Gateway implementation on the pinned tag¶

    1. Register the authoritative catalog¶

    Keep the catalog with the gateway deployment. Stock LiteLLM can load a local OpenAPI JSON file via spec_path and project its operations into MCP tools. The simple search contract can start with a single operation. For a richer contract, inspect the actual served inputSchema. The LTS projection preserves basic types, descriptions and required fields, and places a JSON request body under body. Use a trusted gateway-side MCP catalog or a registry path that preserves native schemas when that projection cannot express the contract.   search_catalog:

    spec_path: /etc/litellm/search-catalog.json
    transport: http
    allow_all_keys: false
    allowed_tools: [web_search]
    allowed_params:
      web_search: [query]
    execution_mode: client  # Proposed field. Add it in the gateway patch.

    2. Mark client-executed catalogs and block gateway dispatch¶

    Add an opt-in execution_mode: client to MCPServerConfig and MCPServer and propagate it through registration and runtime copies. Leave the default as native gateway execution. Config-file registration is sufficient for the first deployment. Start by supporting this mode for the local spec_path catalog. This makes the catalog available without a vendor URL, vendor OAuth flow, or provider credential in LiteLLM. A stock spec_path entry can still reach the OpenAPI HTTP execution handler, so the file alone provides discovery. Config model · Runtime model · Stock OpenAPI execution

    Add the dispatch check at operations.execute_mcp_tool and MCPServerManager.call_tool or equivalent shared points that cover all paths. The checks must cover native MCP, REST, virtual tool dispatch and model-driven execution. In particular, require_approval: "never" on an inference request must be unable to cause native execution of a client-executed tool. Include startup, health, listing and telemetry in the gateway egress verification. MCP and REST execution · Manager dispatch · Model auto-execution

    3. Add the internal authorization-only operation¶

    Add POST /mcp-rest/tools/authorize to the existing MCP REST router and put it in LiteLLMRoutes.mcp_inference_routes. This is a proposed private contract. A stock MCP host only calls its application MCP endpoint. Use the canonical server ID and bare tool name so model prefixes and display names never become policy inputs. The optional tool_call_id is for correlation. Derive the principal from authenticated context. REST call route · Route groups · Acting identity

    4. Wire the application MCP server¶

    The official SDK’s low-level server needs two handlers. The tools/list handler follows the discovery contract above. The tools/call handler follows the steps below. The application-owned tool loop can share the same execution function. SDK server API · MCP result contract

    1. Authenticate the caller and look up the requested tool in the local binding map. Keep the map and provider settings in deployment configuration. The gateway owns the published tool definition. The application owns how an approved definition maps to a fixed backend operation.
    2. Send the proposed arguments, canonical identity and correlation ID to LiteLLM. Require a successful response, affirmative authorized field, matching canonical identity and correctly shaped final arguments. A denial, timeout, unavailable policy service, malformed response or missing binding stops execution.
    3. Invoke the configured backend using only the approved values. A fixed adapter can map names or field shapes to the provider contract. If the application needs to change the requested action or introduce a material argument, obtain a decision for the changed invocation. Keep network timeouts, cancellation, and provider errors distinct from policy denials.
    4. Return a correctly shaped MCP result after any required output check. Expose a sanitized MCP tool error for a well-formed call that policy declines. Keep authorization IDs and provider error details in appropriate audit records. Separate transport authentication errors from argument-level denials.

    Identity at both connections. For interactive Streamable HTTP, use the standard MCP OAuth flow where supported, including protected-resource metadata and audience validation. For headless hosts, use the documented bearer mechanism and issue credentials at the required scope. A token intended for the application MCP endpoint does not become a LiteLLM credential. Use an admitted gateway virtual key for the intended identity or a supported identity exchange. A single shared key applies that service’s policy to every call. Use caller-specific gateway identity where users need different grants or guardrails. For stdio, the launched process receives the required credentials from its deployment environment. MCP authorization · LiteLLM MCP access

    Enforcement boundary. The gateway controls the managed search flow because the application checks with it before using the managed provider credential. An independently credentialed application can call its own provider independently. If the guarantee must apply to all managed provider traffic, put the managed provider credential in the trusted execution component or use provider-side restrictions that enforce this boundary.

    5. Apply output policy at the required point¶

    Guardrail Placement for application execution Consequence
    Catalog description and schema scanning LiteLLM’s runtime listing and current eligibility lookup A hidden tool is absent from discovery and ineligible for a new authorization, even if a host still displays it. Catalog scan
    pre_mcp_call Authorization endpoint before the app can dispatch Blocks or rewrites the exact proposed arguments. Put controls that must prevent outbound traffic here. Precheck
    during_mcp_call Application call lifecycle, when needed Native LiteLLM schedules this alongside its upstream call. It can affect the outcome after egress has started. During hook · Native dispatch
    LLM pre_call LiteLLM inference request containing the tool result Screens what enters the model through that path. It runs after the provider call. The fixture proved the Chat Completions case with role: "tool". Test Responses and Messages separately if using them. Content filter · Lifecycle hooks
    MCP post_mcp_call parity The application sends the actual CallToolResult to a gateway check before release Protects the harness or user who receives the result. Use ProxyLogging.post_mcp_call_hook or an equivalent enforcing path with the correct policy context. Native logging callbacks have distinct error behavior. Unified output hook · Native callback

    For model-input screening only, use a tested LLM pre_call rule on the actual tool-result content. The fixture used the built-in content filter locally in the gateway. The example below illustrates separate input and model-result stages. Set policy scope deliberately because a default-on LLM rule can also apply to other model input. A guardrail that requires a service must use an approved internal path consistent with the gateway’s network policy. MCP guardrail config · Built-in content filter

    guardrails:
  - guardrail_name: web-search-input
    litellm_params:
      guardrail: litellm_content_filter
      mode: pre_mcp_call
      default_on: true
      blocked_words:
        - keyword: blocked-input-fixture
          action: BLOCK
        - keyword: masked-input-fixture
          action: MASK
  - guardrail_name: model-tool-result-screening
    litellm_params:
      guardrail: litellm_content_filter
      mode: pre_call
      default_on: true
      blocked_words:
        - keyword: blocked-output-fixture
          action: BLOCK

    If every consumer must receive a centrally screened result, add a private result check. Bind the result to the authenticated principal, authorized tool, decision ID and applicable call ID. Validate a size-bounded typed result and return the accepted or rewritten result to the application. The application releases only that result. If model admission must enforce this against a faulty application, also check the decision and result correlation at inference admission. A voluntary result endpoint leaves sequencing to the application. MCP result contract · Unified output hook

    Optional entry point for an application that owns the tool loop¶

    On stock v1.108.5 an application can request LiteLLM catalog projection through POST /v1/chat/completions. Include this in tools under the admitted LiteLLM identity. Tool resolution · Chat Completions handoff

    {
  "type": "mcp",
  "server_label": "search_catalog",
  "server_url": "litellm_proxy/mcp/search_catalog",
  "require_approval": "always"
}

    LiteLLM filters the catalog, sends ordinary function definitions to the model and hands the resulting calls back to the app. require_approval: "always" selects the handoff on this path. The application then runs the separate per-call authorization step. The execution_mode: client dispatch check is still required so execution cannot be enabled by changing this request field. Approval switch · Model auto-execution

    {
  "id": "call-example-1",
  "type": "function",
  "function": {
    "name": "search_catalog-web_search",
    "arguments": "{\"query\":\"latest SGLang news\"}"
  }
}

    Resolve the observed model-facing name through the explicit tool map. Assemble complete arguments before authorization, especially for streaming. Run the same decision and execution steps as the application MCP server. In the follow-up completion preserve the preceding assistant message with tool_calls and the exact call ID. The stock proof used non-streaming Chat Completions with a mock model. Function calling · Chat Completions handoff

  "role": "tool",
  "tool_call_id": "call-example-1",

    Operational behavior and upgrade path¶

    • Catalog changes. Use compatible schema changes for existing tool names. For breaking changes, deploy the compatible binding first or use a new tool version. Discovery exposes the current visible catalog. On authorization, validate against the current eligible schema, even if the host is still using an older list. MCP tool protocol
    • Policy and dependency failures. Each new execution requires a current positive decision. Test revocation against the actual cache and database behavior across workers. Use bounded timeouts and distinguish policy denial from temporary unavailability. Keep the provider call count at zero on either outcome.
    • Retries and concurrency. Correlate the model or MCP invocation, gateway decision and provider outcome. Deduplicate a repeated logical call where the app can recognize it. Keep principal and invocation scope in deduplication, and treat a provider timeout as potentially having executed. A policy allow is not a completed search or a billable provider result.
    • Portability. Keep tools/list and tools/call on the public wire, and keep the internal decision API behind the app deployment. A harness upgrade, provider swap, or policy standard change then affects a specific connection. Verify negotiated MCP versions and real model tool calls when changing a host or SDK version. MCP versioning
    • Gateway upgrades. Pin the release and run the acceptance tests before adopting a later gateway build. The prior source review covered v1.109.0, v1.110.0-rc.1 and upstream snapshot 36160145. Those changes include MCP catalog and policy improvements. The pinned patch remains the implementation baseline for this handoff. Stable release · Release candidate
