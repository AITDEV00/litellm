2 How Priority Gets Forwarded

Four stages translate an API key label into a SGLang request body field.

prior1 → 0

API Key
Metadata carries {"priority":"prior1"}
→
⚙️

→
🌉
Priority Bridge
Forwards priority:0 in request body
→
🚀
SGLang
Places prior1 first in queue

SGLang uses --schedule-low-priority-values-first, so priority 0 is highest and 200 is lowest.

When the queue is full, low-priority requests get rejected outright. prior1 never hits this path because it sits first in line and takes the next freed slot, even when the server is completely full.

This contrast, prior1 always served vs prior3 rejected when full, is exactly the behavior the priority feature is designed to produce.

5 Why This Proves the Pipeline

Counterfactual Proof

If the priority field failed to get forwarded, SGLang would assign the lowest possible priority to the prior1 request. It would then sit in the queue just like prior3 and take ~100 seconds.

It took 1.04 seconds. The feature works.
