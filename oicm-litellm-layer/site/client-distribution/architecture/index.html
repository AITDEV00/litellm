    Architecture (v5 — gateway slice, cc-switch configurator)¶

    Revision 5. The installed client is cc-switch-cli (a single static Rust binary), not the lite Python CLI. The end user already holds an admin-issued gateway key, so there is no lite login step and no uv/Python/ wheelhouse mirror tier. The mirror carries only the cc-switch binaries, the installer, and a provider preset. Harness configuration (including a real ~/.config/opencode/opencode.json) is written by cc-switch, which supports 7 harnesses; lite only configured claude and codex.

    Revision 4. Storage moved from a PVC to a cluster-internal RustFS instance (see rustfs.md), which removes the multi-replica problem. All routes nest under /install. /install is unauthenticated.

    Host model¶

                     litellm.ecouncil.ae:443
                          │
                   nginx ingress (unchanged)
                          │  /  ->  litellm-proxy:4000
                          │
                 litellm gateway pod (unchanged deployment)
                          │
        ┌─────────────────┼──────────────────────┐
        │                 │                      │
        ▼                 ▼                      ▼
   /v1/*, /ui       /install/*               RustFS (cluster-internal)
   (upstream,       (slice: generated          rustfs.adeo-litellm:9000
    unchanged)       script + proxied           buckets: client-mirror, logs
                     artifact reads +
                     /install/admin/* writes)

    No ingress changes. The existing Prefix / rule delivers /install/* to the gateway; the slice registers the routes and proxies artifact reads to RustFS. RustFS has no ingress and is reached only over the cluster network.

    Why in-app (unchanged from v2, still the core decision)¶

    • Uniformity. One deployment, one ingress rule, one thing to monitor.
    • The gateway has memory. /install is generated by code that reads general_settings, the request host, and the manifest, so the script always carries the gateway's own canonical base URL.
    • Upstream precedent. The app already mounts StaticFiles for /ui and /swagger, and OICM already serves an APIRouter slice (litellm/proxy/oicm_routes.py) pinned by drop-detection tests. This is the same pattern again.
    • The slice is the RustFS boundary. It does not implement object-storage semantics (RustFS does); it adds auth, path containment, hashing, and manifest consistency, which RustFS cannot.

    Route map (all under /install)¶

    Route Auth Mechanism Content
    GET /install none router handler, generated POSIX bootstrap script
    GET /install/manifest.json none router handler -> RustFS version/hash manifest
    GET /install/cc-switch/<file> none router handler -> RustFS cc-switch release archive / install.sh / checksums
    GET /install/providers/adeo/<harness>/v<N>.json none router handler -> RustFS (baked fallback) versioned per-harness cc-switch preset (canonical shape, sentinels only)
    * /install/admin/* PROXY_ADMIN router handlers -> RustFS write surface (see admin-sync.md)

    The whole surface is one prefix, so the firewall allows litellm.ecouncil.ae and nothing else, and a single ingress rule covers it. The admin sub-path is still separable at the ingress if you later want to restrict writes by network range.

    One consequence to state plainly: because everything shares /install, the public reads cannot be firewalled separately from the admin writes by prefix alone. If that ever matters, split /install/admin into its own ingress rule; it is one path, not a redesign.

    The slice¶

    litellm/proxy/client_distribution/
├── __init__.py          ← re-exports router
├── routes.py            ← APIRouter: /install, /install/*, /install/admin/*
├── generator.py         ← pure script generator (manifest + base URL -> text)
└── storage.py           ← thin S3 client helper shared with the logging config
    • routes.py builds a standalone APIRouter and lazily imports proxy_server globals inside handlers, matching voice_routes.py / oicm_routes.py.
    • Wiring is one line in proxy_server.py next to the existing mounts: app.include_router(client_distribution.router).
    • Drop-detection tests in tests/unit/proxy/test_oicm_drop_detection.py pin the wiring so an upstream merge that clobbers the line fails a test.
    • No StaticFiles mount this time: reads are proxied from RustFS by a handler, because the bytes live in a bucket, not a directory. (That is the one place v4 diverges from v2's mechanism.)

    The full first-run flow¶

    curl -fsSL https://litellm.ecouncil.ae/install | sh
        │
        ▼
  [install script]                    (runs on the dev machine)
        │  uname -s, uname -m, libc detect (MINGW/MSYS -> windows archive)
        │  GET /install/manifest.json
        ▼
  install cc-switch  ──── GET /install/cc-switch/cc-switch-cli-<target>.tar.gz
        │   (mirror of the upstream per-platform release archive + checksums)
        ▼
  cc-switch -> ~/.local/bin/cc-switch
        ▼
  prompt for the user's admin-issued API key
        ▼
  diagnostic: GET <base>/api/v1/models with that key   (abort if it fails)
  -> key-scoped model list, each entry with its real context_length
        ▼
  list the harnesses cc-switch supports; user picks which to configure
  (multi-select, NOT all-by-default — the user may keep a non-gateway config
   for a harness they do not pick)
        ▼
  for each chosen harness:
        read the pinned preset (path, sha256) from the manifest
        GET /install/providers/adeo/<h>/v<N>.json, verify sha256,
        compose with jq (sentinel substitution: base URL + key + models,
        per-model context windows, the manifest's max_output_tokens cap)
        provider add --config-file --overwrite
            (id = adeo-litellm-<last4 of the key>: one stable id per key,
             re-runs overwrite it in place via the fork's upsert flag)
        cc-switch use <id> --app <h>    -> writes that harness's config file
        ▼
  done

    The installer is a generic orchestrator: it knows no per-harness JSON shape, and every harness (claude, codex, gemini included) goes through the same preset + compose + --config-file path. Each harness's cc-switch config structure lives in its own versioned preset slice, pinned by the manifest, so revising one harness touches nothing else.

    No authentication is needed to download the binary or read the manifest. The user's key is only used for the /api/v1/models diagnostic and to fill the provider's apiKey field. cc-switch writes each selected harness's native config file; harnesses not selected are left untouched.

    Sizing and isolation¶

    • No volume in the gateway pod. The gateway holds no artifact bytes; it streams them from RustFS per request, so pod memory is unaffected by artifact size.
    • RustFS is cluster-internal, no ingress, NetworkPolicy allowing only the gateway. Single-node StatefulSet + PVC (see rustfs.md).
    • Multi-replica: no longer a constraint. RustFS is shared, so the gateway can scale out freely. (Open question 8 is resolved and removed.)

    What stays untouched upstream¶

    • cc-switch: byte-identical upstream release archives (mirrored), never rebuilt.
    • The coding harnesses themselves: installed by users through their own channels; cc-switch writes their config.
    • The proxy's config, auth, model list, routing: unchanged apart from the one router include line the drop test pins.
